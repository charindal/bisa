# BISA SIS Project Instructions

## Overview
BISA SIS is a full-stack Java Spring Boot + React TypeScript application for academic identity and access management.

**Backend:** Spring Boot (Java) in `/backend`  
**Frontend:** React + TypeScript + Vite in `/frontend`

## Project Conventions

### Java/Spring Boot Backend
- Package structure: `com.bisa.sis.*`
- Use Spring Boot 3.x with Java 17+
- Repositories inherit from `JpaRepository`
- Services handle business logic; controllers handle HTTP
- Use `@Transactional` for database operations
- Request/response use DTOs
- Validation via `jakarta.validation` annotations
- Integration tests connect to a real Postgres via `spring.datasource` (env vars / `application.yml` defaults) rather than Testcontainers — Docker-in-Docker isn't reliable on this project's CI runners (same reason buildtrac's backend avoids it). Locally that's the `db` service in `docker-compose.dev.yml`; in CI it's the `postgres` `services:` container in `deploy.yml`'s Backend Tests job.
- Flyway migrations in `src/main/resources/db/migration/`

### React/TypeScript Frontend
- Use TypeScript strict mode (no `any` types)
- Component structure: functional components with hooks
- State management: React Context (auth, app state)
- Styling: CSS modules or Tailwind (verify in vite.config.ts)
- API calls via `/src/lib/apiClient.ts`
- Protected routes via `/src/auth/ProtectedRoute.tsx`
- Build tool: Vite
- Tests: Vitest + Playwright (when needed)

### Database
- PostgreSQL (see `docker-compose.yml`)
- Migrations are immutable and version-controlled
- Schema includes audit logging (see `audit/` package)
- Authentication via JWT stored in HTTP-only cookies

### Version Control
- Main branch: `main` (production-ready)
- Development branch: `develop`
- Feature branches: `feature/feature-name`
- Bug branches: `fix/bug-name`
- Commit message format: `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`

## Decision Rules - Decide Without Asking

When you encounter ambiguity, resolve it this way:

| Scenario | Decision |
|----------|----------|
| **Naming:** Variable/function/class name unclear | Use clear, descriptive names; prefer `userRepository` over `ur` |
| **Code style:** Braces, spacing, indentation | Follow existing patterns in the codebase |
| **Testing:** Unit vs. Integration test needed | Write both if feasible; integration tests for DB/API layers |
| **Dependencies:** Add a new library? | Add only if it solves the problem better than custom code |
| **Configuration:** New config property needed | Add to `application.yml` with profiles for dev/prod |
| **Error handling:** Exception or null-check | Use exceptions for errors; null-checks for optional values |
| **Async operations:** Threading/async needed | Use Spring's `@Async` or virtual threads (Java 19+) |

## Communication
- When implementing tasks, show the plan first if it involves architectural changes
- For complex refactors, explain the rationale before making changes
- Always run tests after making changes to verify nothing broke
- Provide brief summaries of what was done and why

**You ask:** "Add user role management to the backend"

**I do (autonomously):**
1. Create `Role.java` entity and `UserRole.java` join table
2. Create `RoleRepository` and `UserRoleRepository`
3. Create `RoleService` with CRUD operations
4. Create `RoleController` with endpoints
5. Add Flyway migration for schema
6. Write unit and integration tests
7. Run tests to verify
8. Show you the changes and ask: "Ready to commit, or need changes?"

**You reply:** "Looks good, commit it"

**I then:** Commit and ask "Push to develop branch?"
